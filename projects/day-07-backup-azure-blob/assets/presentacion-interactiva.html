Proyecto · Backup Azure Blob

¿Qué pasa si Azure falla después de copiar?

La copia local ya ha sido verificada, publicada y sigue siendo utilizable. Azure es una publicación remota opcional, no el único punto de éxito.

Local primero.

El diseño protege una copia válida antes de intentar la fase remota y comunica una degradación segura si la publicación Azure no puede completarse.

Flujo contractual

Primero se conserva una copia confiable.

Cada fase prepara la siguiente; la publicación Azure ocurre únicamente después de una publicación local correcta.

01 · ORIGEN

Seleccionar

Archivo o directorio regular permitido por el contrato.

02 · VALIDACIÓN

Planificar

Rechaza rutas inseguras, conflictos y relaciones peligrosas.

03 · TEMPORAL

Copiar aislado

La copia no aparece aún como resultado final.

Comparar

06 · AZURE

Publicar remoto

Sube archivos publicados con prefijo backups/.

Opcional

Resultado clave: si la fase remota falla después, el resultado local permanece disponible.

Seguridad e integridad

Controles explícitos antes de confiar.

El proyecto prefiere rechazar una entrada ambigua o insegura antes que producir una copia difícil de verificar.

↯

Sin enlaces

Se rechazan enlaces simbólicos, junctions de Windows y entradas especiales tanto en la validación como en la verificación.

⊘

Sin sobrescritura

La publicación local falla ante un destino final existente; la subida remota usa overwrite=False.

#

SHA-256 efímero

Se comparan rutas, tamaños y hashes por archivo durante la operación, sin persistir los hashes como inventario.

◇

Secretos fuera del repo

La configuración Azure usa variables de entorno no versionadas; ni cadenas de conexión ni valores sensibles forman parte del proyecto.

Estrategia de pruebas

Validar el contrato sin exponer secretos.

Una evidencia revisable

La suite local no necesita red, SDK activo ni una cuenta Azure para demostrar el comportamiento contractual.

  • Fixtures sintéticos y manifiestos de referencia.
  • Pruebas de núcleo local, CLI y errores controlados.
  • Adaptador Azure aislado con clientes falsos.
  • Diagnósticos sin valores de configuración.
1

Local: copia temporal, verificación exacta y limpieza de artefactos propios.

2

CLI: las variables Azure faltantes bloquean la mutación local antes de crear contenido.

3

Azure: dobles prueban prefijos, ausencia de sobrescritura y fallo de proveedor controlado.

Comprobación operativa documentada: se confirmó el SDK y una sesión de Azure CLI sin exponer datos. Cuando no existen credenciales contractuales autorizadas, no se ejecuta transferencia real; la validación del adaptador se sostiene con dobles.
